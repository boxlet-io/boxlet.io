Whitepaper

The future of containers isn't containers.

Not smaller containers. Not faster containers. Containers rethought from the ground up.

Precious Okwu, Kiri, 22 November 2026

We've done this once already. For years we made virtual machines lighter: smaller images, faster boots, better schedulers. That isn't what changed things. What changed things was a different question: what does an app actually need from the machine? The answer was a process with its own view of the system, not a whole computer. So we stopped shrinking virtual machines and built containers.

It's time to ask that question again. A container still carries a Linux userland it barely uses, and it can still ask the kernel for almost anything. Most of the work on containers today makes them smaller and faster: slimmer base images, distroless builds, quicker runtimes. Kiri does that too, and it's good work. But it's still the same box.

Ask what code actually needs, and the answer is smaller again: its own memory, a short list of things it may call, and nothing else. WebAssembly gives us exactly that, and it runs everywhere: on any CPU, in any operating system, on a server, at the edge, in a browser.

Rethinking from the ground up also means leaving the old habits behind. The teams that won with containers didn't treat a container as a small virtual machine. They dropped SSH, init systems and hand-tended servers. Boxlets have to drop container habits the same way, or we'll just rebuild the old box out of new parts.

That's how I'm rethinking containers. I'm pivoting to boxlets.

Each step had deep roots before it took over: virtualization ran 32 years before VMware, and chroot came 34 years before Docker. WebAssembly shipped in 2017. Its turn is next.

The architecture, and the part WebAssembly plays

Linux namespaces made containers possible. WebAssembly makes boxlets possible. Here is the whole stack, from your code down to the machine it runs on.

Your codeRust, Go, Python, JavaScript or C, compiled to WebAssembly.Keep your language. Nothing to rewrite to start.
WebAssembly standards
WebAssemblyA portable instruction format. One compiled file runs on any CPU and any operating system, in its own block of memory.The unit of code. No operating system inside.
WASIThe standard list of things code may ask for: files, clocks, random numbers, sockets, HTTP.Permissions by name. A boxlet gets only the ones you grant.
Component modelTyped interfaces between pieces of code, whatever language each was written in.Boxlets fit together through declared interfaces, not guesswork.
Distribution
RegistryBoxlets are stored as standard OCI artifacts of type application/wasm, next to your container images.Push, pull, tag and sign the way you do today.
Boxlet
Orchestrator, in RustDecides where each boxlet runs, grants its imports, routes its requests, and runs Linux images as containers beside it.One API for both kinds.
Engine on each machineWasmtime, built into the orchestrator's agent. It compiles each boxlet ahead of time and runs thousands of isolated instances in one process.An instance per request, created in a fraction of a millisecond and gone after it.
Where it runs
AnywhereLinux servers, Macs, Windows, the edge. amd64 and arm64.One build for every machine.

The WebAssembly, WASI, component model and OCI artifact layers are open standards that exist today. The orchestrator and its agent are what we're building.

The habits we're leaving behind

Containers carried some habits over from virtual machines. Boxlets start without them.

ContainersBoxlets
What you shipA Linux userland with your app insideOnly your compiled code
Which CPUOne image per architectureOne file for every CPU
PermissionsEverything the kernel offers, minus a deny-listNothing, plus what you grant by name
LifetimeA process that waits for workAn instance per request, gone after it
IsolationKernel namespaces and cgroups for each containerThe engine's sandbox, thousands per process
Connecting servicesHTTP over a virtual networkTyped interfaces, and HTTP when you need it
