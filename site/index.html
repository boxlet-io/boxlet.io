Containers, rethought from the ground up.

We didn't get containers by shrinking virtual machines. We got them by asking what an app really needs. A boxlet asks that again: it holds only your compiled code, runs as WebAssembly on any machine, and reaches only what you give it.

What it leaves out

Each step in the history of servers took something out of the package. A virtual machine carried a whole operating system. A container shared the host's kernel but still carried a Linux userland. A boxlet carries only your compiled code and a list of what it needs from outside.

How many fit on one machine

We wrote one small program, a check that blocks container images with no version tag, and ran it as a Python container, a Go container and a Rust boxlet. Move the slider to see how the idle memory adds up as you run more of them.

Idle memory per program: 12.6 MB as a Python container, 5.8 MB as a Go container, 1.0 MB as a boxlet, plus about 2 MB once for the WebAssembly engine. The containers ran all the time, waiting for work. A boxlet can also be loaded for each call and use nothing between calls. Measured in Kiri's Linux VM on an Apple silicon Mac on 20 November 2026. Your own services will use more, so measure them.

It reaches only what you hand it

A container can ask the Linux kernel for anything, unless a filter says no. A boxlet can't make system calls at all. It gets a short list of imports, and you decide each one.

A container

About 390 system calls on x86-64 Linux. Docker's default filter blocks about 44 of them.

world check {
  import wasi:http/outgoing-handler@0.2.0;
  import wasi:clocks/wall-clock@0.2.0;
  export check: func(image: string)

}

The whole list of what this check can reach. No files, no sockets, no environment, unless you add them.

Beside your containers, not instead of them

One registry holds both kinds of image. An orchestrator reads what each one is and runs it the right way: a WebAssembly image as a boxlet, a Linux image as a container. Both get the same network, logs and limits, so you can move one service at a time.

services:
  check:
    image: team/check:1.4  # WebAssembly: a boxlet
  api:
    image: team/api:3.2    # Linux: a container
  db:
    image: postgres:17     # Linux: a container
How we want it to work. This isn't released yet.

The orchestrator is written in Rust. It embeds the Wasmtime engine as a library, so the scheduler and the engine are one program, memory-safe, with no garbage collector pausing the process that holds every boxlet.

Good as boxlets

  • Functions and webhooks
  • Policy checks and admission rules
  • Plugins
  • Tools an AI agent calls

Keep as containers

  • Databases such as Postgres and Redis
  • Programs that fork, or read /proc
  • GPU jobs
  • Anything that needs a full Linux

Why now

The idea is old. The standard it needed shipped in the last three years.

  1. 2013Docker makes the container the thing everyone ships.
  2. 2019Docker's founder writes: "Webassembly on the server is the future of computing."
  3. 2024WASI 0.2 gives WebAssembly a standard way to reach files, sockets and HTTP.
  4. 2025WebAssembly 3.0 adds garbage collection and 64-bit memory, so more languages fit.
  5. 2026WASI 0.3 makes async native.
  6. NextBoxlets, running beside your containers.

Boxlet is in development

We're building it at Kiri, a small, fast container runtime for Mac, Windows and Linux, written in Rust. Kiri runs your Linux containers today. Boxlets are what we're adding next, so both kinds run under the same commands. The essay has the full argument, the sources and what still falls short.
